# Локальная генеративная модель: память, нагрузка и стоимость

Расчет на 21 октября 2026 года. Рассматриваем полную замену генеративного API на **Qwen3.6-35B-A3B**, указанную в разрешенном перечне кейса. Веса не скачивались, сервер не арендовался, локальный inference не запускался. Код runtime и конфигурация приложения этим документом не меняются.

**Практический выбор:** для первых проб — одна GPU 24 GB с Q4_K_M, коротким контекстом и одной активной генерацией; для запаса памяти — 32 GB с той же квантовкой. Для авторского FP8 или GGUF Q8_0 предпочтительна GPU 48 GB. Для 3–5 пользователей сначала нужна очередь к одной модели, а не пять копий модели. Производительность и качество этих вариантов требуют замера. Существующая CPU ВМ 4 vCPU / 16 GB недостаточна для полностью резидентной Q4 модели вместе с приложением.

## Что именно размещаем

`A3B` означает около 3 млрд активных параметров на токен, но не размер всех весов в памяти. У MoE модели должны быть доступны все эксперты. Для расчета используем опубликованные файлы, а не формулу «3B × число байт». Генеративные роли — извлечение фактов, анализ, проверка и планирование — могут обращаться к одному экземпляру модели. Локальные E5 и OCR остаются отдельными компонентами.

| Вариант | Опубликованный размер | Приблизительно GiB | Разумный исходный вариант |
| --- | ---: | ---: | --- |
| ggml-org Q4_K_M, текстовые веса | 20,4 GB | 19,00 | llama.cpp, GPU 24/32 GB либо CPU с достаточной RAM |
| ggml-org Q8_0, текстовые веса | 36,9 GB | 34,37 | llama.cpp, GPU 48 GB |
| Авторский Qwen FP8, репозиторий | 37,5 GB | 34,92 | vLLM на совместимой GPU 48 GB; фактические загруженные тензоры профилировать |
| ggml-org BF16, текстовые веса | 69,4 GB | 64,63 | Не помещается целиком на одну GPU 24/32/48 GB |

GB здесь десятичные, GiB = GB × 10^9 / 2^30. Размер файла или репозитория не равен пиковому потреблению VRAM. В FP8 репозитории есть дополнительные компоненты; режим text-only может исключать часть загрузки, но неизвестную экономию заранее не вычитаем. GGUF projector и MTP/draft-файлы не нужны для исходного текстового сценария. Скачивать весь репозиторий со всеми квантовками не требуется. [GGUF от ggml-org](https://huggingface.co/ggml-org/Qwen3.6-35B-A3B-GGUF/tree/main), [авторские FP8 файлы](https://huggingface.co/Qwen/Qwen3.6-35B-A3B-FP8/tree/main).

Квантование не гарантирует ту же точность, что удаленный checkpoint. Открытая локальная Qwen не обязана воспроизводить поведение шлюза с неизвестными настройками. Отдельно проверяем русский анализ, JSON, атрибуцию банку и условные выводы. [Авторская модель](https://huggingface.co/Qwen/Qwen3.6-35B-A3B).

## Память и контекст

В конфигурации Qwen — 40 слоев, из них 10 full-attention; 2 KV heads, head dimension 256. Остальные слои используют linear attention с состоянием. Поэтому нельзя рассчитывать ее KV cache как у dense Transformer с 40 обычными attention-слоями. [Авторский config.json](https://huggingface.co/Qwen/Qwen3.6-35B-A3B/raw/main/config.json), [реализация гибридных слоев llama.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/models/qwen35moe.cpp).

Нижняя оценка только обычного KV cache при FP16:

```text
KV_bytes = 2 × full_attention_layers × KV_heads × head_dim
           × bytes_per_element × context_tokens × active_sequences
         = 20 480 × context_tokens × active_sequences
```

| Контекст одного вызова, включая ответ | Обычный KV, 1 активная последовательность | Обычный KV, 5 активных последовательностей |
| --- | ---: | ---: |
| 8 192 токена | 160 MiB | 800 MiB |
| 16 384 токена | 320 MiB | 1 600 MiB |
| 32 768 токенов | 640 MiB | 3 200 MiB |

Это **не полный бюджет inference**: дополнительно нужны recurrent state, его возможные checkpoints, временные тензоры prefill, CUDA context, graph capture, runtime и запас свободной памяти. Их объем зависит от движка, batch и GPU. Для первичной закупочной оценки закладываем отдельный запас **несколько GiB**, а окончательную конфигурацию принимаем по профилированию пика. vLLM прямо указывает, что контекст, число последовательностей и CUDA graphs влияют на память. [vLLM memory guide](https://docs.vllm.ai/en/stable/configuration/conserving_memory/).

| Сервер | Память и режим | Вывод до замера |
| --- | --- | --- |
| 1 GPU 24 GB | Q4 около 19 GiB + KV + остальные буферы; сначала 8K, одна активная генерация | Возможный минимальный GPU вариант. Запас узкий; 16K и полную выгрузку на GPU нельзя обещать без проверки |
| 1 GPU 32 GB | Q4; сначала 8K–16K, одна активная генерация | Предпочтительнее по запасу. Q8/FP8 целиком не рассчитываем: одни веса больше 32 GB |
| 1 GPU 48 GB | Q8 либо FP8; сначала 16K, одна активная генерация | Основной кандидат для меньшей потери точности. 3–5 параллельных генераций проверяются отдельно |
| CPU-only | Q4, 8–16 vCPU, желательно 64 GB RAM, одна генерация | Возможен функциональный резерв; интерактивная задержка неизвестна |

Используем фактическую доступную VRAM из диагностики, а не только название тарифа. V100, A6000, L4 и L40S имеют разные архитектуры и поддержку вычислений. В частности, V100 не выбираем для нативного FP8: для нее рассматриваем GGUF Q4/llama.cpp с отдельной проверкой поддержки. Наличие формата в списке движка не гарантирует совместимость именно этого MoE checkpoint и GPU. [vLLM: аппаратная совместимость квантований](https://docs.vllm.ai/en/stable/features/quantization/).

Для отдельного GPU inference-хоста: 8 vCPU, **32 GB RAM минимум как исходная конфигурация для Q4, 64 GB предпочтительно**; для Q8/FP8 — ориентир 64 GB. Если PostgreSQL, E5 и приложение живут там же, начинать с 64 GB. SSD 100–150 GB под один выбранный checkpoint, окружение, контейнеры, compile cache и данные. Это инженерные ориентиры, не замер потребления. Для CPU-only выбираем 64 GB RAM и SSD 150 GB; mmap/своп на 16 GB не превращают сервер в подходящий для рабочего демо.

## Один запрос и 3–5 пользователей

Начальная конфигурация — один процесс inference, один активный LLM вызов и ограниченная очередь приложения. Все агенты используют те же веса. Восемь последовательных обращений увеличивают работу, но не требуют восьми копий модели. На GPU 24 GB не включаем пять активных слотов только потому, что пять человек открыли сайт.

При FIFO по целой задаче и времени обработки карточки `T` пять одновременных задач могут завершиться примерно через `T`, `2T`, …, `5T` плюс работу инструментов. Это арифметика очереди без новых поступлений, не SLA. Принимать новую работу нужно с учетом длины очереди и таймаута. Время поиска и HTTP не обязательно должно удерживать GPU слот.

Для llama.cpp явно фиксируем контекст, число слотов, размер prefill batch и предел ответа. Семантику общего контекста и контекста на слот проверяем на закрепленной версии: не предполагаем, что `-c 16384 -np 5` автоматически дает 16K каждому. У движка есть отдельный `--kv-unified-per-slot`. [Параметры llama-server](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md).

Для FP8/vLLM исходный профиль — text-only, `max_model_len=16384`, `max_num_seqs=1`; затем измеряем возможность 2 и 3–5 последовательностей. Это параметры для будущей проверки, не протестированная команда развертывания. Авторская карточка рекомендует vLLM ≥ 0.19.0 и описывает `--language-model-only`. [Deployment автора](https://huggingface.co/Qwen/Qwen3.6-35B-A3B-FP8#vllm). После запуска проверяем реальный объем cache и оценку concurrency в логах; она характеризует память, а не обещает скорость. [vLLM: concurrency](https://docs.vllm.ai/en/stable/serving/parallelism_scaling/).

Модель думает по умолчанию. Для коротких структурированных ответов исходный расчет предполагает non-thinking, настроенный через chat template, и ограничение **всех** выходных токенов. Промпт `/nothink` не заменяет корректную настройку Qwen3.6. Включение thinking меняет расход и задержку. [Параметры автора](https://huggingface.co/Qwen/Qwen3.6-35B-A3B#instruct-or-non-thinking-mode).

## Нагрузка по нашим отчетам

Прочитаны только числовые агрегаты локальных `data/processed/llm-full-development-suite-v11.local.json` и `llm-live.db`, база открыта read-only. Содержимое публикаций, ответы, идентификаторы вызовов и ключи сюда не перенесены. Выборки небольшие и включают разные маршруты; медианы отдельных этапов нельзя складывать как результат одной карточки.

| Маршрут в v11 | Выборка | Входные токены, медиана | Выходные токены, медиана | Квитанция, медиана |
| --- | ---: | ---: | ---: | ---: |
| Извлечение + его проверка | 6 пар | 1 347 | 160,5 | 0,038372 единицы |
| Анализ + semantic review без исправления | 10 пар | 9 019,5 | 415 | 0,1832985 единицы |
| Полная новая карточка, ровно 4 вызова без исправления | 5 карточек | 10 400 | 554 | 0,221241 единицы |

У полной четырехвызовной карточки диапазоны: 8 859–10 586 входных, 521–651 выходной токен; квитанция 0,199596–0,232223. В уникальных вызовах этого прогона максимальный вход — 5 237 токенов. Значит 8K — разумный первый smoke-профиль, но новая сеть до 8 вызовов должна проверяться заново. Суммарные 10K токенов на карточку не означают 10K одновременно в одном контексте.

`x-litellm-response-cost` пока имеет **неподтвержденную денежную единицу**. В локальном учете выставлен `receipt_rub_per_unit=1`, но это настройка, а не доказательство тарифов RUB. Все сравнения ниже используют множитель `r = рублей за одну единицу квитанции`.

Сеть из 8 обращений может переиспользовать длинный контекст и выдавать больше текста. Удвоение четырехвызовного маршрута дает только сценарий чувствительности `0,442482 × r`, а не измеренный тариф будущей сети. Реальную нагрузку считать как суммы токенов по каждому вызову, включая планировщик, проверки и исправления.

Для задержки используем формулу, а не чужой показатель tokens/s:

```text
T_card ≈ Σ(input_tokens_i / measured_prefill_rate_i
           + output_tokens_i / measured_decode_rate_i
           + per_call_overhead_i) + tool_time + queue_time
```

Нужны отдельно prefill, decode и пиковая память на наших запросах. Например, при условно измеренных 20 output tokens/s только выдача 554 токенов заняла бы 27,7 секунды, без входа и очереди. Если восемь вызовов суммарно выдадут 4 000 токенов, при той же скорости только decode займет 200 секунд. **20 tokens/s здесь условие формулы, не замер какой-либо GPU/CPU.**

## Когда локальная модель дешевле API

Сравниваем дополнительные расходы на inference: обычное приложение нужно в обоих вариантах. Не включены труд команды и потери от простоев. Для API используем именно наблюдаемую квитанцию, а не неподтвержденную цену за миллион токенов.

```text
C_api_cold = cards × 0,221241 × r
C_api_warm = cards × 0,1832985 × r
N_break_even = C_local_week / C_api_per_card
```

Извлечение переиспользуется для того же неизменяемого источника, например между CFO и CEO. Сейчас записи источников привязаны к компании: отдельные копии одной публикации для разных компаний могут повторно оплачивать извлечение. Поэтому warm-сравнение применимо только при фактическом попадании в кэш, а общий межклиентский кэш потребует отдельного проектирования с сохранением ACL. Дополнительные планировщики и проверки новой сети изменят знаменатель.

| Вариант | Недельная база сравнения | Новых 4-call карточек при r=1 | Карточек без повторного извлечения при r=1 |
| --- | ---: | ---: | ---: |
| Selectel L4, только минимальный compute | от 11 739,84 ₽ | от 53 064 | от 64 048 |
| Yandex T4i, обычный compute | 29 760,66 ₽ | 134 517 | 162 362 |
| Cloud.ru V100 + выбранный диск/IP | 41 426,52 ₽ | 187 247 | 226 006 |
| Cloud.ru CPU 8/64 + выбранный диск/IP | 4 480,43 ₽ | 20 252 | 24 444 |

Количество округлено вверх. Для Selectel цена и порог — нижние границы без SSD/IP. При `r=10` число карточек уменьшается в десять раз, при `r=100` — в сто. Например, нижняя граница L4 становится примерно 5 307 либо 531 карточка; до подтверждения `r` это только чувствительность расчета. Для USD тарифа формула: `USD_week × фактический_RUB_per_USD / (0,221241 × r)`; текущий курс и банковские комиссии здесь не предполагаются.

Для единственного измеренного теплого v8 примера нижний порог L4 при условном `r=1` получается
`ceil(11 739,84 / 0,271701)` = **43 209 карточек/неделю**, без SSD/IP и нового извлечения. Один пример
не задает универсальную стоимость сети: дополнительные запросы, инспекция и исправление изменят результат.

Даже достижение денежного порога не доказывает, что сервер успеет обработать объем. Для нижнего порога L4 53 064 карточки за неделю одна последовательная очередь должна в среднем завершать карточку не дольше **11,4 секунды** при непрерывной полной загрузке. Для V100 денежный порог требует около **3,23 секунды**. Достижимость не измерена; если нужны дополнительные GPU, изменится и стоимость.

Если все восемь вызовов окажутся точным удвоением четырехвызовной работы, соответствующие пороги уменьшатся вдвое. Это не измерение новой сети. При небольшом количестве демопользователей и подтверждении `r=1` постоянная аренда GPU по этим тарифам экономически не обоснована одной лишь экономией на API; локальный запуск может быть нужен по другим требованиям.

Отдельный ориентир: весь установленный в кейсе бюджет API на семь дней составляет `500 × 7 = 3 500 ₽`. Даже минимальный опубликованный непрерывный GPU compute из таблицы дороже этого потолка; реальное потребление API может быть значительно меньше. Это сравнение бюджетов, оно не подтверждает единицу квитанции и не отменяет технических причин размещать модель локально.

Для краткого локального демо дешевле оплачивать только окно работы: минимальный Selectel compute на 2/4/8 часов ежедневно дает соответственно 978,32 / 1 956,64 / 3 913,28 ₽ за семь дней, **сверх хранения и иных услуг**. Остановка вычислений не означает прекращение оплаты дисков. Это вариант планирования расходов, не бесплатный хостинг.

## Проверка перед окончательным выбором

1. Закрепить checkpoint/quant hash, версию движка, CUDA и фактический GPU. Для старого V100 отдельно подтвердить поддержку Qwen hybrid/MoE kernels; сначала короткий текстовый запуск.
2. Повторить текущие контрольные случаи локально. Проверить выводы по источникам вручную, а не только валидность JSON. Локальный reviewer той же модели не считается независимым подтверждением качества.
3. Замерить холодный старт и повторные вызовы: TTFT, prefill/decode, peak VRAM/RAM, полный `T_card`, стоимость аренды, 8K и 16K. Не переносить чужие tokens/s в наш расчет.
4. Прогнать 1, затем 3 и 5 пользователей с одной активной генерацией и очередью. Отдельно проверить сеть до 8 вызовов, таймаут, отмену и завершение после исчерпания лимита.
5. Только после этого пробовать batching или несколько активных последовательностей. Сравнить ускорение и пиковую память с последовательным режимом. Бюджет токенов, проверка evidence и лимиты задач остаются общими.

Для первого технического прототипа локальной замены достаточно **одной 32 GB GPU с Q4, 64 GB RAM, 100–150 GB SSD и очереди**. Если критична меньшая потеря точности — **48 GB и Q8/авторский FP8 на совместимом GPU**, также начиная с одной генерации. Минимальный 24 GB вариант требует проверки запаса VRAM; CPU-only — проверки приемлемого ожидания. Бесплатную недельную замену API для такого checkpoint текущие подтвержденные GPU тарифы не дают.
