# Подготовка данных компаний

Первый реализованный модуль — `backend/src/alphich/data.py`. Он читает три CSV, формирует нормализованные профили, рассчитывает признаки выбранных компаний и сохраняет версионированный снимок для будущих API и ранжирования новостей. Runtime использует только стандартную библиотеку Python.

## Вход и запуск

Ожидаются файлы `df_Uid_data_hack.csv`, `df_Uid_payment_hack.csv` и `df_Fid_Uid_link_hack.csv`, UTF-8 с разделителем `;`. BOM поддерживается. Обязательные колонки проверяются до обработки; неправильная структура файла останавливает запуск без публикации частичного снимка.

```sh
PYTHONPATH=backend/src python3 -m alphich.data \
  --input-dir data/raw \
  --output-dir data/processed/run-001 \
  --company-id U_9250 \
  --company-id U_99802 \
  --company-id U_44792 \
  --top-n 10
```

Без `--company-id` выбираются пригодные `CLIENT` с `REVENUE_COMPANY > 15000000000`. Порог можно изменить через `--min-revenue-raw`. Единицы выручки в CSV не установлены: это числовой фильтр по исходному полю. Явный выбор ID позволяет включить профиль с неизвестной выручкой; неоднозначный или отсутствующий ID вызывает ошибку.

Выходной каталог должен быть новым. Снимок сначала формируется во временном каталоге на том же файловом разделе и публикуется переименованием после успешной обработки. При ошибке ранее подготовленные файлы не изменяются.

## Результат

| Файл | Содержимое |
| --- | --- |
| companies.jsonl | Все пригодные профили; исходные значения сохранены в source_fields, строка указана в source_record |
| contexts.jsonl | Профили выбранных компаний и восемь признаков с ID, версиями и source_refs |
| quality.json | Качество исходного набора, количество строк, пропуски, повторения и область отбора |
| quarantine.jsonl | Некорректные записи и неоднозначные компании с причинами и номерами записей |
| manifest.json | SHA-256 входов и выходов, версии метода/схемы, параметры выбора и правила единиц |

`source_record` — номер записи данных с единицы, без строки заголовка. Это не обязательно номер физической строки CSV, если источник содержит переносы внутри ячейки.

Числа денежных полей обрабатываются через Decimal и записываются строками. Доли представлены числами от 0 до 1; при нулевом знаменателе — null. Валюта, период платежей, единицы выручки и дата профиля остаются null. После изменения входов, отбора, top-N или версии метода меняются версии контекста и ID признаков.

## Правила качества

- Если один ID имеет разные профили, исключаются все его варианты. В карантин попадает ID и список записей; одинаковые профили учитываются один раз.
- Пустые продуктовые флаги остаются неизвестными. Некорректные значения отмечаются в quality_flags, а не превращаются в false.
- Несоответствия ФТС и стран сохраняются явно. Страны нормализуются удалением пробелов и повторений; импорт, экспорт и валюта из них не выводятся.
- Название `NEGATIVEMARK` не интерпретируется: исходное поле сохранено без присвоения недокументированного смысла.
- Некорректные суммы, нечисловые/бесконечные значения и дробное количество платежей исключаются с причиной. Количество строк и узлов в отчете относится к явно указанной стадии проверки.

## Платежные признаки

Платежи читаются последовательно. Для глобального поиска повторений в памяти хранятся SHA-256 отпечатки нормализованных строк и направленных пар; также хранятся профили и агрегаты соседей выбранных компаний. Память не является константной по объему набора. Полный CSV не загружается в список; большие повторные выборки в будущем можно вынести в SQL.

Для входящих и исходящих потоков отдельно рассчитываются сумма, количество платежей, число контрагентов, концентрация, доля потока с известными профилями, известная внутригрупповая доля и отрасли известных соседей.

1. Self-payments сохраняются в сырой статистике, но исключаются из контрагентных признаков.
2. Повтор нормализованной строки учитывается один раз. Разные строки одной пары суммируются с флагом неоднозначности. Это выбранная демо-политика: без периода и ID операций нельзя доказать, что повтор ошибочен.
3. Неизвестные и quarantined контрагенты входят в общий знаменатель; их отрасль остается неизвестной.
4. Top-N ограничивает только показанные списки. Все доли рассчитываются до ограничения и используют весь соответствующий поток.
5. При отсутствии платежей доля покрытия и концентрация неизвестны, а не равны нулю. Признак не доказывает отсутствие риска.

Отрасль и профиль контрагента определяются только из пригодных исходных профилей. Платежная связь не называется поставкой или продажей. Связи физических лиц сводятся к количеству связанных людей и других компаний; владение и должность не предполагаются, сами person ID в признаки не передаются.

## Проверка

В `backend/tests/test_data.py` проверяются бизнес-инварианты на вымышленном наборе: карантин конфликтующих профилей, строгий порог отбора, исключение self-payments, обработка повторов, полные знаменатели, неизвестные контрагенты и пустые потоки, поврежденные числа, связи через физлиц, воспроизводимость и смена версий, защита готового снимка и отсутствие частичного результата при ошибке схемы.

Полный прогон исходного набора подтвердил 85 513 пригодных профилей, 102 выбранных CLIENT и обработку 1 380 585 платежных строк. Обнаружены 27 406 self-payment строк, 17 дополнительных повторов направленной пары и одна повторная нормализованная строка. Один ID с 12 конфликтующими профилями исключен. После карантина профиль известен у 63 606 узлов платежного графа; число 63 607 в первоначальном исследовании относилось к набору до карантина.

## Следующий потребитель

API сможет получать контекст по company ID; механизм отбора — читать проверенные отрасль, продукты, ФТС и платежные агрегаты. Каждый существенный клиентский вывод ссылается на ID признака и его версию. В LLM передается необходимая часть профиля, а не вся таблица или необработанные source_fields. Загрузка в PostgreSQL и HTTP маршруты — следующий этап реализации.
