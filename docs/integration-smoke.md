# Интеграционный стенд Alphich (P0)

Этот этап объединяет существующие компоненты, **не изменяя** `backend/app/intelligence/` и `knowledge/`.
Пять сервисов уже определены в `compose.yaml`: `postgres`, `api`, `worker` (ingestion),
`analysis-worker` (инсайты и вопросы) и `frontend`. Оба worker и API используют один `DATABASE_URL`
и общие таблицы `llm_budget_days`/`llm_calls`, которыми управляет готовый provider.

## Первый запуск на Mac с Docker Desktop

Из **корня** репозитория:

```bash
cp -n .env.example .env
# В локальном .env должны быть DEMO_COMPANY_IDS=DEMO_A,DEMO_B и пароль существующей БД.
# Не коммитьте .env: в нём могут быть секреты и API-ключи.
docker compose up -d --build
docker compose ps
python3 scripts/verify-stack.py --import-fixtures
```

Проверка импорта выполняется только если отсутствует указанный профиль. Скрипт **не вызывает**
`--replace`, **не удаляет** том PostgreSQL и не перезаписывает чужой набор компаний.
При пустой БД используется `backend/fixtures/companies.csv`. Для исходных обезличенных CSV
организаторов используйте `DEMO_COMPANY_IDS=U_9250,U_99802,U_44792` и отдельную команду
импорта из `backend/README.md`, не смешивая два набора данных.

На других машинах сначала проверьте доступность Docker: этот стенд не запускался в контейнере
автора патча, где отсутствует бинарник `docker`.

Проверочный адрес UI: http://127.0.0.1:5173. Swagger: http://127.0.0.1:8000/docs.

## Что проверяет `scripts/verify-stack.py`

Без дополнительных параметров скрипт:

- подтверждает, что запущены все 5 контейнеров, отвечает health API и Nginx;
- создаёт `DEMO_A`/CFO демосессию и читает профиль;
- публикует **новую синтетическую** новость через `POST /publications` с новым `Idempotency-Key`;
- ждёт завершения *ingestion-worker*, читает `GET /jobs/{id}`, `GET /events/{id}` и `GET /sources/{id}`;
- проверяет сохранение текста и отсутствие ложного `url_verified=true`;
- проверяет страницу событий, историю задач и запрет доступа другой компании к источнику/событию/задаче;
- читает `/llm/status` (сумма расходов/резервов общей БД) и `/companies/{id}/feed`.

Можно объединить запуск и проверку:

```bash
python3 scripts/verify-stack.py --start --import-fixtures
```

**По умолчанию вызовов LLM нет**. Скрипт лишь читает показатель расхода из БД.

## Проверка настоящего analysis-worker (ТОЛЬКО с разрешения владельца бюджета)

Убедитесь, что команда подтвердила:

1. `LLM_BASE_URL`, `LLM_API_KEY`, реальные разрешённые ID моделей и проверенные цены в локальном `.env`;
2. `LLM_PRICES_CONFIRMED=1` и достаточный остаток дневного бюджета;
3. корпус и индекс находятся в `data/processed/bank-index-v1`, модели E5 — в `data/models/e5-base`;
4. `GET /api/v1/llm/status` возвращает `configured: true` и `bank_index_present: true`.

Только после подтверждения ответственного за общий ключ:

```bash
python3 scripts/verify-stack.py --live-analysis --analysis-timeout 600
# Ещё один платный вопрос, если он действительно нужен:
python3 scripts/verify-stack.py --live-analysis --ask-question --analysis-timeout 600
```

Команда с `--live-analysis` ставит реальную задачу через `POST /companies/{id}/insights`,
ждёт `analysis-worker`, получает `/insights/{id}`, `/runs/{id}` и `/evidence/{id}`.
`--ask-question` дополнительно ставит `POST /insights/{id}/questions` и читает `/answers/{id}`.
Без установленного шлюза/цен/индекса скрипт завершится с ошибкой **до** платного запроса.
Результат может быть `insufficient_evidence`: проверка показывает правдивые ограничения, а не
подменяет реальную модель подготовленной карточкой. Фактическое содержимое AI-ответа требует
ручной оценки соответствия источникам.

**Примечание о полном стенде:** `docker compose up -d --build` уже включает `analysis-worker`,
но без настроенного ключа этот процесс не может генерировать карточки. Это не ошибка фронтенда.

## Новый интерфейс

Раздел «Аналитика» показывает сохранённую персонализированную ленту через GET `/feed`
и никогда не запускает платный анализ при открытии страницы. В карточке события есть блок
«Влияние на компанию». Он показывает `/llm/status` и предлагает явно нажать «Сформировать инсайт».
После `202 Accepted` интерфейс проверяет `/jobs/{id}`; на `succeeded` получает `/insights/{id}`.
Вкладки тезисов разделяют `news_fact`, `company_fact`, `bank_view`, `model_inference`; ссылки
на evidence вызывают `/evidence/{id}?insight_id=…`, не являются выдуманными URL.
При вводе вопроса используется `/insights/{id}/questions`, отдельное задание и `/answers/{id}`.
Журнал вызывает `/runs/{id}`. Для ошибки или отсутствия LLM выводится явное состояние,
без обещания готового инсайта.

Сервер проверяет ACL и роль по демосессии для этих маршрутов. Открытие чужих карточек/вопросов
не обходится простым изменением ID. Секрет шлюза остаётся только в окружении API/analysis-worker;
браузер получает только значения ответа `/llm/status`, не ключ API.

## Тесты, ограничения, владение файлами

```bash
cd backend && python -m pytest -q && cd ..
cd frontend && npm install && npm run build && cd ..
python3 -m unittest discover -s scripts/tests -v
```

На хосте автора этого патча нет Docker, а в окружении не загружены npm-зависимости, поэтому
проверка контейнеров/браузера должна пройти на машине команды. Не утверждаем, что реальная
генерация с моделями или расход бюджета проверены без доступа к выданному шлюзу.

**Не менялись:** `backend/app/intelligence/`, `knowledge/`, схемы БД, условия бюджета.
**Ответственные:** изменения названных каталогов и подтверждение model ID/цен — через коллегу,
ведущего LLM-контур. Пакет frontend использует публичные HTTP-контракты, не импортирует
внутренние классы агента.

Если `analysis-worker` не успевает, смотрите журналы без публикации ключей:

```bash
docker compose ps
docker compose logs --tail=100 analysis-worker
docker compose logs --tail=100 worker
```
