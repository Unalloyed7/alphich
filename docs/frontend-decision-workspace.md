# Третья итерация: понятное рабочее пространство

Основание — критерии кейса «Новостная аналитика» из презентации Альфа-Банка, страницы 9–10 и 14, и референсы Альфа-Бизнеса, предоставленные командой. Предыдущий обзор: [frontend-redesign.md](frontend-redesign.md).

## Что реализовано и зачем

| Задача пользователя | Изменение | Связь с критериями |
| --- | --- | --- |
| Быстро вернуться к важному | Избранное, непрочитанные события, отметка «Новое» | Удобство и завершённость пользовательского сценария |
| Найти событие или раздел | Видимый поиск, Ctrl/Cmd+K или `/`, стрелки и Enter | Доступная точка входа, меньше лишних переходов |
| Понять, откуда взялся вывод | Состав разбора: факты новости, данные компании, позиция банка, интерпретация AI; переход к нужной группе подтверждений | Персонализация, источники, разделение экспертной позиции и выводов модели |
| Оценить актуальность материала | Название, дата и страница банковского источника рядом с позицией банка | Проверяемость и временная применимость |
| Понять работу системы | Журнал с понятными названиями этапов; технические сведения раскрываются отдельно | Прослеживаемость анализа и использования признаков компании |
| Сообщить об ошибке | «Полезно», «Не для моей компании», «Есть неточность» и комментарий; явное сохранение на сервере | Обратная связь для проверки качества и персонализации |
| Продолжить работу после перезагрузки | Ссылки на события, разделы и фильтры, поддержка «Назад/Вперёд» | Полный пользовательский сценарий |
| Работать с клавиатуры и телефона | Клавиатурные вкладки, управление фокусом, адаптивные диалоги, увеличенные области нажатия и более читаемый текст | Доступность и удобство |

Эта итерация развивает существующую визуальную систему: тёмная сводка, спокойные светлые карточки, ограниченные смысловые цветовые акценты. Новые элементы служат работе с аналитикой; дополнительные декоративные показатели не вводятся.

## Границы поведения

- Избранное и прочтение содержат только ID событий. По возможности сохраняются в `sessionStorage` текущей вкладки отдельно по компании и роли. Между устройствами не синхронизируются; при недоступном хранилище работают до перезагрузки.
- Быстрый поиск охватывает уже загруженную персональную ленту, загруженные события и пять разделов. Он не обещает поиск по всей базе. Генерация и платные вопросы не запускаются поиском или открытием карточки.
- Ссылка вида `#/insights?filter=bookmarks&event=event-1` не содержит токен. Получателю нужна собственная разрешённая сессия; доступ к компании, роли и материалам проверяет сервер. Состояние избранного получателю не передаётся.
- Счётчики состава разбора показывают число утверждений, а не процент достоверности. Автоматическая проверка не выдаётся за экспертную оценку. Неизвестная дата материала так и обозначается.
- Журнал показывает действия, полученные из API; незнакомые действия имеют нейтральное название с доступными техническими сведениями. Стоимость — сумма учтённых вызовов данного запуска, с отметкой о неподтверждённой части, если она есть.
- Оценки относятся к конкретному разбору и текущей демосессии. Новая авторизация создаёт другую сессию. В рамках сессии оценку можно изменить. Это не журнал всех изменений и не учёт постоянных банковских пользователей.

## Серверная обратная связь

Добавлены `GET` и `PUT /api/v1/insights/{insight_id}/feedback`. Значения: `useful`, `not_relevant`, `needs_review`; комментарий до 500 символов. Запись меняется только после явного подтверждения. Ошибки сервера не превращаются в сообщение об успешном сохранении.

Таблица `insight_feedback` создаётся существующим `Base.metadata.create_all` при старте актуальной версии API. Первичный ключ: хеш демосессии + ID разбора. Вместе с оценкой сервер сохраняет компанию, роль, ID и версию события, версию профиля, ID запуска и версии анализа. Клиент не может подменить этот контекст. Токен в таблицу не записывается. Проверки доступа такие же, как при чтении разбора, включая текущие ограничения банковских документов.

Перед интегрированной демонстрацией нужно пересобрать API и фронтенд из одной версии. Старый API отвечает 404 на новый маршрут — интерфейс честно сообщает о недоступности оценок. Текущая итерация не перезапускает уже работающие контейнеры и не запускает платную генерацию.

## Как использовать оценки для контроля качества

Сбор оценок уже работает. Экспертная очередь, административный экран, агрегирующий API и автоматическое переобучение не реализованы. Для защиты можно предложить следующий процесс, явно называя его планом:

1. Эксперт регулярно разбирает `needs_review` и `not_relevant`, сопоставляет комментарий с сохранённой версией разбора и исходными подтверждениями.
2. Размечает причину: ошибка факта, неподходящий профиль, устаревший банковский материал, неподдержанный вывод или проблема интерфейса.
3. Команда добавляет подтверждённые случаи в регрессионный набор и сравнивает версии на одном наборе до выкладки.
4. В отчёте показывает размер выборки и отдельные показатели: доля `useful` среди всех оценённых карточек, доля `not_relevant`, доля `needs_review`, доля подтверждённых экспертом ошибок и время их разбора. Показатели считаются по последним оценкам на пару сессия/карточка, с разбивкой по версии анализа и роли.

Оценки добровольные и смещены в сторону мотивированных пользователей; их недостаточно для независимой оценки точности. Нужна отдельно размеченная экспертами контрольная выборка. Доля оценённых просмотров требует серверной телеметрии просмотров, которой сейчас нет: локальное «прочитано» для такого показателя использовать нельзя.

## Проверки

- TypeScript и production build.
- 11 браузерных сценариев: сводка, состояния данных, фильтры, источники, вопросы, действия генерации, смена компании, избранное, прочтение, поиск, глубокие ссылки, история браузера, происхождение выводов, сохранение оценок и недоступность API.
- Размеры 320/390/768/1024/1440 px; отдельная проверка поиска и карточки на 320 px. Клавиатура, возврат фокуса, отсутствие горизонтального переполнения, axe WCAG 2 A/AA и 2.1 AA на проверяемых состояниях.
- Серверная регрессия: `test_insight_feedback.py`, `test_api_contracts.py`, `test_intelligence.py`, `test_llm_scopes.py` — 84 passed, 1 skipped. Проверены запись/изменение/чтение, разделение сессий и ролей, доступ к документам, валидация и отсутствие запуска моделей при оценке.

Браузерные данные синтетические и перехватываются тестами; серверные проверки используют TestClient и тестовую БД. Они не подтверждают качество реальных выводов LLM. Автоматическая доступность не заменяет ручную проверку со скринридером и пользовательское тестирование. Локальный Python 3.14 использован с временным NumPy вне репозитория для выполнения регрессии; проектные зависимости не изменены, модель эмбеддингов в этих проверках не загружалась.
