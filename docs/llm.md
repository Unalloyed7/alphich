# LLM анализ и подключение к приложению

В `backend/app/intelligence/` реализован путь «событие → извлечение цитируемых фактов → персональный отбор → банковский RAG → собственный агент → проверенная карточка → уточняющий вопрос». API ставит задачи в PostgreSQL; отдельный `analysis-worker` выполняет генеративные вызовы и не задерживает worker загрузки публикаций.

**Доступа к шлюзу организаторов пока нет.** HTTP-протокол, очереди, бюджет, проверки и диалог проверены тестовым шлюзом. Локальная E5 и банковский индекс проверяются настоящими файлами. Качество генерации реальной разрешённой модели, её задержка, формат usage и цены ещё не измерены. Тестовые ответы не используются как fallback в приложении.

## Настройка шлюза

Скопируйте `.env.example` в `.env`. Заполните серверные переменные после получения доступа:

| Переменная | Значение |
| --- | --- |
| `LLM_BASE_URL` | Адрес шлюза до `/chat/completions`, например база с `/v1`; реальный адрес выдаёт организатор |
| `LLM_API_KEY` | Секретный ключ, только на сервере |
| `LLM_EXTRACTION_MODEL`, `LLM_ANALYSIS_MODEL` | Реальные model ID шлюза; можно использовать один ID для обоих этапов |
| `LLM_MODEL_CATALOG_JSON` | JSON-массив model ID, семейства из кейса, цен в RUB за миллион токенов и лимитов |
| `LLM_PRICES_CONFIRMED` | `1` только после подтверждения тарифов и того, какие токены учитываются в usage |
| `LLM_DAILY_LIMIT_RUB` | Общий суточный лимит проекта, больше 500 отклоняется |
| `BANK_ALLOWED_DOCUMENT_IDS` | `*` — загруженный корпус; список ID через запятую — ограниченный доступ; пустая строка — ни одного документа |

Структура элемента каталога ниже содержит **заполнители**, которые надо заменить; это не действующие ID и не тарифы:

```json
{
  "id": "MODEL_ID_FROM_ORGANIZERS",
  "case_model": "qwen3.6-35b-a3b",
  "input_rub_per_million": "CONFIRMED_INPUT_PRICE",
  "output_rub_per_million": "CONFIRMED_OUTPUT_PRICE",
  "input_limit": 32768,
  "output_limit": 2500
}
```

В `.env` весь массив задаётся одной строкой в одинарных кавычках. Цены — неотрицательные десятичные строки. `input_limit` — подтверждённый предел входных токенов, `output_limit` — поддерживаемый `max_tokens`. Для проверочного прохода runtime использует консервативный предел по UTF-8 байтам входа с запасом на служебные токены; точный tokenizer шлюза пока не подтверждён. При превышении вход отклоняется, скрытого обрезания prompt нет.

Допустимые `case_model`: `gemma4-26b-a4b`, `glm-5.3-flash`, `qwen3.6-35b-a3b`, `deepseek-v4.1-flash`, `qwen3-vl-30b-a3b-instruct`, `kimi-k2.6`. Это внутренние ключи наименований из кейса, а не предположение о доступных model ID. Неизвестное семейство, отсутствующая цена или неподтверждённая конфигурация блокируют вызовы.

Клиент использует HTTP chat completions: `messages`, `model`, `max_tokens`, `stream=false`. Он не требует SDK, native tool calling или `response_format`. Шлюз должен возвращать JSON в `choices[0].message.content`, нормальное завершение и целочисленные `usage.prompt_tokens`/`usage.completion_tokens`. Совместимость конкретного шлюза проверяется до живого демо.

## Запуск

Подготовьте индекс и локальную модель по [инструкции RAG](rag.md). В контейнеры монтируются `data/processed` и `data/models` в режиме чтения; веса и PDF не включаются в образ.

```sh
docker compose up -d --build postgres api worker analysis-worker frontend
docker compose run --rm api python -m app.intelligence.cli status
```

Без ключа и каталога status показывает `configured=false`, а запрос анализа возвращает `503 llm_not_configured`. Импорт компаний и загрузка исходных публикаций продолжают работать. Для новой схемы добавляются отдельные таблицы; существующие таблицы и данные не сбрасываются. `create_all` — текущий bootstrap прототипа, полноценные миграции ещё не внедрены.

После подтверждения адреса, ID и цен выполните **один настоящий оплачиваемый пробный вызов**, который тоже проходит через общий бюджет:

```sh
docker compose run --rm api python -m app.intelligence.cli probe --live
```

Он проверяет JSON и usage для `LLM_ANALYSIS_MODEL`. Если модель extraction отличается, её совместимость дополнительно проверяется первым реальным сценарием. Не включайте автоматические повторы на стороне HTTP-клиента или прокси.

Для запуска без Docker:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt -r knowledge/requirements-rag.lock
PYTHONPATH=backend:backend/src:knowledge/src .venv/bin/python -m app.intelligence.cli status
```

Переменные `.env` в этом режиме должны быть экспортированы в окружение процесса. Для RAG дополнительно задайте `BANK_INDEX_DIR`, `E5_MODEL_DIR` и `E5_MODEL_MANIFEST` путями на своей машине. Контейнерные пути из Compose не подходят для запуска на хосте.

## Что подключает интерфейс

Сначала используйте существующий `POST /api/v1/publications` и дождитесь завершения его job: результатом будет исходный `event_id`. Анализ запускается отдельным явным запросом, а не для каждого произведения «компания × публикация».

| Запрос | Результат |
| --- | --- |
| `POST /companies/{id}/insights` | `202` и job; тело `{ "event_id": "…", "as_of": "…" }`, дата необязательна |
| `GET /jobs/{id}` | Состояние задачи; при успехе `result_type=insight` или `answer`, `result_id` |
| `GET /jobs?operation=insight_analysis` | История задач анализа текущей демосессии; для вопросов `operation=insight_question` |
| `GET /insights/{id}` | Проверенная карточка либо `insufficient_evidence` |
| `POST /insights/{id}/questions` | Новая job; тело `{ "question": "…" }` |
| `GET /answers/{id}` | Ответ с теми же видами тезисов и проверками |
| `GET /evidence/{id}?insight_id=…` | Неизменяемое доказательство из конкретной карточки |
| `GET /evidence/{id}?insight_id=…&answer_id=…` | Доказательство из ответа, включая дополнительно найденные источники |
| `GET /runs/{id}` | Действия, проверка, версии, токены, стоимость и удержанные резервы |
| `GET /companies/{id}/feed` | Отбор по последним 100 доступным на `as_of` событиям, со ссылками на подходящие готовые карточки |
| `GET /llm/status` | Готовность конфигурации и общий бюджет за день UTC |

Все пути имеют префикс `/api/v1` и требуют `X-Demo-Session`. POST анализа и вопроса требуют новый `Idempotency-Key` длиной 8–128 символов; повтор того же ключа/тела возвращает ту же задачу. Другое тело с тем же ключом даёт 409. Компания и роль наследуются от серверной сессии. В вопрос нельзя передать другую дату, роль, профиль или расширенный доступ.

При анализе из ленты передавайте её `trace.as_of`, чтобы сохранить срез и переиспользовать кэш. При повторе запроса после сетевой ошибки сохраняйте исходный `Idempotency-Key`. Новый ключ и новая дата означают новую задачу. Поля модели отображайте как текст; внешние ссылки берите из серверных записей evidence.

Пример постановки анализа с уже полученным event ID:

```sh
curl -X POST http://127.0.0.1:8000/api/v1/companies/DEMO_A/insights \
  -H "X-Demo-Session: $ALPHICH_DEMO_TOKEN" \
  -H 'Idempotency-Key: analysis-example-001' \
  -H 'Content-Type: application/json' \
  --data '{"event_id":"EVENT_ID_FROM_INGESTION"}'
```

`failed` с `error=budget_exceeded` отличается от отсутствующих доказательств: первое — отказ задачи по расходам, второе — сохранённая ограниченная карточка. При ошибке шлюза, неизвестном usage, невалидном JSON или отклонённой проверке готовая аналитика не публикуется. Кнопки и отображение этих новых DTO ещё должен подключить разработчик интерфейса.

## Извлечение и агент

Извлечение кэшируется по неизменяемому источнику, версии, hash, модели и версии extractor. Отдельная запись блокирует повторную параллельную генерацию. Сначала модель предлагает дословные уникальные цитаты; сервер сам определяет Unicode spans. Затем отдельный вызов проверяет все тематические атрибуты цитат. В API указано `verification_method=exact_quote_and_separate_llm_entailment`; это автоматическая проверка, не ручное подтверждение истинности новости.

Обрабатывается префикс до 6500 UTF-8 байт исходного текста. Для длинных публикаций сохраняются точный диапазон, `extraction_coverage.complete=false` и `partial_extraction_bounded_source_prefix`; факты за пределами окна не считаются извлечёнными. Полное покрытие длинных статей потребует пакетного прохода по дополнительным окнам и отдельного бюджета. Неоднозначная или отсутствующая цитата отбрасывается. При отсутствии проверенных фактов/применимости результат `insufficient_evidence` не содержит придуманных выводов.

Собственный агент получает проверенные признаки компании, событие, причины отбора и первые банковские результаты. Разрешены `search_bank_materials`, `search_related_events`, `get_company_features`, `get_payment_neighbors`, `get_evidence`, `finish`. Параметры даты, компании и доступа в их схемах отсутствуют; SQL, shell и сетевой загрузчик модель не выбирает. Отдельные идентификаторы физлиц в prompt не включаются. Связанные события ищутся среди допустимых сохранённых событий; инструмент не запускает скрытое извлечение остальных статей. Платёжные соседи доступны, только если в переданном профиле уже есть рассчитанные payment features; базовый API импорта компаний их пока не загружает.

До восьми обращений к модели на задачу **включая extraction, отдельные проверки и исправление**, до восьми дополнительных инструментов, одно исправление карточки. Число оплачиваемых запросов сохраняется в БД и переживает перезапуск worker. Одинаковый инструмент без новых аргументов не выполняется повторно. Для первых PDF-запросов используется последний завершённый день UTC; отсутствие банковского результата сохраняет новость и явно отражается в ограничениях.

Карточка разделяет `news_fact`, `company_fact`, `bank_view`, `model_inference`. Первые три копируют серверный текст доказательства. Банковская оценка ссылается на проверенный bank claim и его PDF/page/span; известный пересмотренный прогноз нельзя заменить старым совпадающим прогнозом из контекста. Числа разрешены в дословных фактах, а модельные выводы формулируются без чисел. Каждый персональный вывод требует новости, признака компании и условий. Риски/возможности ссылаются на ID выводов; действия — на ID тезисов и условия. Заголовок формируется сервером из заголовка события.

После проверки структуры, ID, типов и чисел отдельный вызов проверяет смысловую поддержку тезисов и действий. При отклонении допускается одно исправление с повторной проверкой в том же лимите. Модельная проверка может ошибаться; оценка на независимо размеченных реальных публикациях остаётся обязательной после получения доступа к шлюзу.

## Кэш и бюджет

Карточка кэшируется по профилю, событию, версиям доступных связанных событий, роли, точному `as_of`, версии runtime, моделям, банковскому индексу и его доступу. Отдельная lease по ключу кэша предотвращает параллельную генерацию одинаковой карточки. Переиспользование extraction не зависит от роли. Ответ на вопрос сохраняет исходные профиль, роль, событие и дату; новые данные компании не подмешиваются. При смене банковского индекса ответ может использовать сохранённые доказательства, но поиск по изменившемуся индексу отключается. Изменение серверной политики документов проверяется при выдаче сохранённого результата.

Бюджет хранится в PostgreSQL целыми микро-рублями. До каждого HTTP-вызова атомарно резервируется стоимость полного разрешённого входа и максимального ответа; после ответа — сверка usage. Таймаут, обрыв или неизвестный usage удерживают резерв. Неопределённый вызов не отправляется автоматически повторно, в том числе после перезапуска worker. Неопределённое общее извлечение также блокирует повторный платный проход: для восстановления нужны проверка квитанции шлюза и явное решение оператора, а не удаление резерва вслепую.

Учёт общий для процессов с одной БД, день определяется по UTC и времени реального вызова. Внешние вызовы других участников напрямую по тому же ключу этот ledger видеть не может: используйте один общий сервис или учитывайте их при настройке меньшего лимита. Ключ не возвращается через API, ошибки провайдера не раскрывают тело ответа или заголовки авторизации. Снижение общего лимита учитывается всеми worker; другой процесс не может увеличить уже установленный дневной лимит.

## Проверки

```sh
cd backend
../.venv/bin/python -m pytest -q
```

Тесты используют вымышленные ответы шлюза и реальные API, SQL, очереди, HTTP-адаптер и проверки. Есть отдельный HTTP-тест с временным портом на `127.0.0.1`, конкурентное резервирование бюджета, таймаут без повтора, отсутствие usage, поддельные цитаты/числа, отказ смысловой проверки, одно исправление, кэш, история, права и диалог со старым снимком профиля. При наличии локального индекса и E5 выполняется интеграционный тест с настоящим поиском банка и тестовой генерацией.

Compose прошёл проверку конфигурации; сборка и полный контейнерный запуск на этой машине пока не проверены, поскольку Docker daemon не запущен. После выдачи шлюза остаются live probe, прогон новой реальной публикации, проверка качества и стоимости и подключение UI к перечисленным API.
