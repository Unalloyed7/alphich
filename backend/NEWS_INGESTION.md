# Прием публикаций, RSS и очередь

Реализован независимый от LLM вертикальный срез **публикация → DB → job → worker → raw event**. Результат работы worker — сохраненная новая публикация и **сырой, ещё не проанализированный event**. Ни одно поле не выдается за извлеченный или проверенный AI-факт.

## Автоматический сбор RSS

`app.rss` читает RSS 2.0 / Atom, скачивает страницы статей и извлекает их текст через Trafilatura.
В [конфигурации](app/rss_sources.json) закреплены семь лент: две [официальные ленты ЦБ](https://www.cbr.ru/development/RSS/)
(пресс-релизы и новости/выступления), Интерфакс, Строительная газета, CNews, Агроинвестор и Elec.ru.
По умолчанию каждая опрашивается раз в 15 минут; обрабатываются первые 10 допустимых уникальных ссылок.
RSS Интерфакса общая: `article_path_prefixes: ["/business/"]` оставляет только экономический раздел.
Фильтр применяется до лимита десяти статей и повторно к конечному адресу после redirect и кешу.
Политические/спортивные записи не занимают лимит скачивания. Пустой экономический срез допускается.
Это текущий ограниченный срез ленты, не архив всех прошлых публикаций.

| Лента | Отраслевой контекст |
| --- | --- |
| `interfax-business` | Экономика, регулирование, промышленность, транспорт и сырьё |
| `stroygaz` | Строительство и недвижимость, включая U_9250/U_99802 |
| `cnews` | ПО и ИТ-оборудование, включая U_44792 |
| `agroinvestor` | Сельхозсырьё и продукты, включая зернового оптовика U_20244 |
| `elec` | Электрооборудование и энергетика, включая U_88715 |

Это распределение источников по темам. Все новости поступают в общий пул для разрешённых компаний;
персональную значимость определяет отбор, а не сам факт подписки на ленту. В CNews разрешены только
основные домены `cnews.ru`/`www.cnews.ru`; тематические поддомены подключаются явно при необходимости.

Из корня репозитория, после импорта компаний и установки `.env`:

```sh
# Поднимает пять основных сервисов и дополнительный RSS-сборщик.
docker compose --profile news up -d --build
docker compose logs --tail=50 rss-collector

# Разовый принудительный опрос: активная lease другого сборщика не обходится.
docker compose --profile news run --rm rss-collector python -m app.rss --once --force

# Состояние расписания и безопасные коды ошибок, без HTTP-запросов к источникам.
docker compose --profile news run --rm rss-collector python -m app.rss --status
```

Сборщик работает только для импортированных компаний из `DEMO_COMPANY_IDS`. Необязательный
`RSS_COMPANY_IDS` в `.env` сужает этот список; максимум 20 компаний. До импорта выводится
`waiting_for_company_import`, а сетевые запросы не выполняются. Процесс проверяет расписание каждые
15 секунд; время следующего опроса и ошибки сохраняются в БД и переживают перезапуск.

Скачанный текст хранится в `rss_articles` один раз на канонический URL; членство в лентах —
в `rss_feed_articles`. Для каждой компании создаются собственные `SourceDocument` и `publication_ingest`
job с устойчивой дедупликацией `rss_deliveries`. Обычный `worker` превращает их в события. События видны
в разделе «События» после обновления списка; завершённый источник доступен через прежний API.
Системные задания не принадлежат браузерной демосессии и не входят в её историю `/jobs`.
Новые компании получают ограниченный сохранённый срез и при ответе HTTP 304.

Для полученных статей `kind=rss_article`, `fetched_at` содержит фактическое время загрузки,
`completeness=extracted_article_text`. `url_verified=true` означает успешную загрузку ссылки,
а не подтверждение истинности новости или полноты извлечения. Дата берётся из RSS/Atom с часовым
поясом; отсутствующая или неоднозначная дата остаётся неизвестной. Время загрузки её не заменяет.

Платные LLM-задачи сборщик не создаёт. Извлечение фактов и персональный инсайт запускаются отдельно
существующей кнопкой/API; релевантность определяет прежний модуль отбора новостей.

URL лент и точные разрешённые домены задаёт оператор в `app/rss_sources.json`; произвольная ссылка из
браузера не становится целью скачивания. Загрузчик проверяет каждый redirect и все DNS-адреса,
подключается к проверенному IP с исходным TLS SNI и проверкой сертификата. Локальные/служебные адреса,
нестандартные порты и понижение HTTPS блокируются. Размер ответа и распакованного gzip ограничен 2 MB,
HTTP-попытка — 25 сек, redirects — три; XML DTD/entities запрещены.

HTTP ETag/Last-Modified позволяют пропустить неизменившуюся ленту. Если статья не скачалась,
валидаторы ленты сбрасываются, ошибка сохраняется и выполняется повтор с задержкой до обычного
интервала. HTML без содержательного текста и PDF отклоняются; RSS-анонс не выдаётся за статью.
Платные страницы и JavaScript-страницы могут не извлечься. Сохранённые статьи неизменяемы:
обновления текста по прежнему URL и семантическое объединение перепечаток пока не реализованы.
При смене доменов, путей, URL или размера выборки прежние ETag не используются. Отпечаток настроек
хранится в отдельной добавочной таблице `rss_feed_selections`, включая пустые ленты; ранее созданные
таблицы сборщика менять или удалять не нужно. При HTTP 304 к сохранённым статьям применяются текущие
ограничения. В отчёте `feed_items` — число распознанных записей ответа 200, `filtered` — исключённые
по разделу, `rejected` — ссылки за пределами допустимых URL/доменов.

Локальный запуск из корня репозитория с тем же `DATABASE_URL`, что у API/worker:

```sh
PYTHONPATH=backend:backend/src:knowledge/src python -m app.rss --once --force
PYTHONPATH=backend:backend/src:knowledge/src python -m app.rss
```

Свою конфигурацию можно передать через `--config /path/rss.json`; список конкретных компаний —
повторяемым `--company-id`, внутри серверного allowlist. `--force` доступен только с `--once`.

Проверено с семью настоящими лентами и пятью профилями U_9250/U_99802/U_44792/U_20244/U_88715:
при лимите одной статьи на ленту загружены шесть статей и создано 30 событий (по шесть на компанию).
В текущем ночном срезе Интерфакса экономических записей не было: 22 записи отфильтрованы по разделу,
3 спортивные ссылки отклонены по домену. Повторный опрос оставил 30 событий, не скачал статьи
повторно и не создал платных задач. События прочитаны через API. Отчёт — локальный
`data/processed/rss-seven-sources-live.local.json`. Проверка выполнена на хосте с отдельной временной
SQLite БД; контейнерный запуск этого сборщика требует проверки на Docker-стенде команды.

## API

Все HTTP-маршруты начинаются с `/api/v1`. Для всех, кроме `health` и `demo-session`, требуется `X-Demo-Session`. `Idempotency-Key` обязателен для `POST /publications`, 8–128 символов (ASCII letters/digits/`._:-`). Токен получают через `POST /demo-session` для компании из серверного `DEMO_COMPANY_IDS`.

| Метод | Маршрут | Семантика |
| --- | --- | --- |
| POST | `/publications` | Принимает JSON `{title,text,source_url?,published_at?}` и отвечает HTTP **202** с job |
| GET | `/jobs/{id}` | Только автору демосессии: `queued/running/succeeded/failed`, `result_id` |
| GET | `/events/{id}` | Только в компании демосессии: сырой event с источником, без неподтвержденных фактов |
| GET | `/sources/{id}` | Только в компании демосессии: оригинальный текст и метаданные источника |

Пример:

```sh
# Запуск в корне репозитория, предварительно импортировав профили через app.importer
# Результат demo-session необходимо передать в переменную TOKEN.
TOKEN="YOUR_DEMO_TOKEN"

curl -i -X POST 'http://127.0.0.1:8000/api/v1/publications' \
  -H 'Content-Type: application/json' \
  -H "X-Demo-Session: $TOKEN" \
  -H 'Idempotency-Key: demo-key-2026-09-11-001' \
  -d '{
    "title":"Банк России сохранил ключевую ставку",
    "text":"Банк России сообщил о сохранении ключевой ставки на очередном заседании. Сведения об условиях кредитных договоров конкретных компаний в публикации не приводятся.",
    "source_url":"https://example.com/source",
    "published_at":"2026-09-11T12:30:00+03:00"
  }'

# Полученный id из ответа — JOB_ID:
curl -H "X-Demo-Session: $TOKEN" "http://127.0.0.1:8000/api/v1/jobs/$JOB_ID"
# После succeeded result_id — EVENT_ID:
curl -H "X-Demo-Session: $TOKEN" "http://127.0.0.1:8000/api/v1/events/$EVENT_ID"
```

В Docker worker работает отдельным сервисом. При локальном запуске API и worker должны иметь **одинаковый `DATABASE_URL`**:

```sh
cd backend
python -m app.worker --once            # попытаться выполнить одну задачу
python -m app.worker --poll-interval 1  # постоянно читать очередь
```

## Источники и ограничения

- `published_at` необязателен, но если задан, требует явный часовой пояс и нормализуется в UTC. `event_at` остается `null`: дата публикации сама по себе не подтверждает дату события.
- `received_at` — время принятия сервером. Для ручной публикации `fetched_at=null`: API не скачивает `source_url`. Такая ссылка отображается как **непроверенная** (`url_verified=false`).
- `completeness=user_supplied_text`: сервис не утверждает, что вставленный текст — полная публикация.
- Сразу после ingestion `topics=[]`, `facts=[]`, `topic_method=not_classified`, `extraction_status=pending_extraction`. Отдельный [LLM worker](../docs/llm.md) извлекает и проверяет факты по явной задаче анализа.
- Для сохранения оригинальной атрибуции дедуплицируются только публикации с одинаковыми **нормализованными текстом, заголовком, URL, опубликованной датой** в пределах одной компании. Однотипный текст из разных источников пока создает два события; объединение связанных событий — отдельная стадия.
- Профиль компании и роль не отправляются в LLM (LLM не вызывается). Пользовательский текст и ссылки не исполняются. `source_url` — справочная ссылка, не точка скачивания.
- При отправке того же payload с тем же `Idempotency-Key` возвращается исходный job, включая итоговый статус. Повтор ключа с другим payload дает 409. Разные ключи могут возвращать разные jobs на одно и то же событие.
- `jobs` доступны **только той демосессии**, которая их создала; `sources/events` доступны другим разрешенным демосессиям **той же компании**, но не других компаний. Это демо-политика, не production RBAC.

## Надежность и эксплуатация

- Задания выбираются compare-and-swap обновлением состояния; на PostgreSQL работают несколько воркеров. Результат и отметка `succeeded` сохраняются в одной транзакции.
- `running` имеет lease 90 сек и атомарно перевыдается после истечения. Максимум 3 попытки; после сбоя результат `failed` с безопасным кодом. Большие генерации LLM требуют отдельного heartbeat/продления lease в следующей итерации.
- Ссылка на исходный документ и `content_hash` сохраняются. При отсутствии новых событий `process_next_job` возвращает False, в режиме daemon воркер спит между опросами.
- `Base.metadata.create_all` — только инициализация MVP, **не миграции**; перед совместной работой с таблицами нескольких версий необходимо внедрить Alembic. Полный тест PostgreSQL/Docker на данном этапе не выполнен (локальные тесты используют SQLite).
- RSS подключён отдельным процессом; анализ, инсайты и вопросы обслуживает отдельный LLM runtime. Ingestion worker сохраняет публикации без генерации выводов.

## Запуск проверок

```sh
cd backend
python -m pip install -r requirements.txt
pytest -q
```

Контрольные случаи: 202 + последующая обработка, корректная дата UTC, запрет доступа другой компании/сессии, дедупликация с разными idempotency keys, 409 при конфликте, 422 на неверный URL/дату, повторное получение результата, истекшая lease, остановка на третьем сбое, отсутствие выдуманных facts.
